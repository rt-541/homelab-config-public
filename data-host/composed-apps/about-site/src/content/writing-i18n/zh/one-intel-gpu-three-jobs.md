这张显卡是 Intel Arc Pro B70: Battlemage，32 GB，通过直通方式分配给了名为 devastator 的 RHEL 虚拟机。它最初是为一个任务购买的，即为 NanoClaw 队列上的代理提供本地语言模型服务。结果它却承担了三个任务：语言模型、Plex 硬件转码（还有一个批量活动通过 VAAPI 将 4K 重新封装的视频重新编码以节省磁盘空间），以及从今天起，将 3D 渲染图像转换为照片。

## 让显卡显示出来

了解这张显卡的驱动程序是 `xe`，并且设备 ID 必须包含在其中。RHEL 10.0 的内核中没有这个 ID。从 9.6 升级时，订阅版本被固定为 10.0，因此 `dnf update` 没有将内核向前推进。将版本设置为 10.2 并更新后，引入了一个带有回溯设备 ID 的 Red Hat 签名内核，重启后显卡就出现了：

```
Kernel driver in use: xe
```

与渲染节点一起，从 `linux-firmware` 加载了 GuC 和 HuC 固件。Plex 容器已经挂载了 `/dev/dri`，在没有更改的情况下看到了新的渲染节点。

## 使用 vLLM 提供模型服务

vLLM 从 Intel 的 llm-scaler 镜像（`intel/llm-scaler-vllm:0.14.0-b8.3.1`）运行，它通过自己的 oneAPI 和 Level Zero 堆栈与显卡通信，这与 Plex 使用的媒体驱动程序是分开的。提供的模型逐步升级：Qwen2.5-7B，然后是 Qwen3-14B（AWQ 版本），接着是 Qwen3-30B-A3B 的测试。

30B 是一个专家混合模型，每个 token 激活约 3.3B 个参数，因此它像一个小模型一样进行解码。Intel 的方案只显示它分布在两个或更多的卡上，因为它们以 FP16（约 61 GB）运行，或者在运行时进行量化，这首先会将完整的模型加载到主机内存中。已经量化为 INT4 的检查点大约是 17 GB，适合一个 B70。它必须使用 GPTQ：在这个镜像中，只有 GPTQ 检查点对 MoE 层使用量化方法。

对于代理来说，有两个设置很重要。第一个是上下文。代理框架本身发送大约 16k 个 token 的提示和工具模式，因此窗口扩展到了 32k，然后在 7B 上使用静态 YaRN 扩展到了 64k（比其 32k 基础增加了 2 倍，这是 Qwen 文档中提到的方法）。第二个是工具调用。在没有解析器的情况下，模型会以纯文本形式返回其工具调用；启用 Hermes 解析器后，它们会以真正的调用形式返回：

```
- --enable-auto-tool-choice
- --tool-call-parser
- hermes
```

## 为 Plex 留出空间

vLLM 在启动时会占用显卡的固定份额。这个份额从 0.75 增加到 0.80，再到 0.92，最终稳定在 0.85，这样就为 Plex 留出了大约 4.8 GB 的空间：两个 4K HDR 转码任务，每个大约需要 2 GB，再加上一些驱动程序的余量。第三个流则会回退到 CPU。模型几乎没察觉到这一点；KV 缓存仍然有足够的空间处理许多并发请求。

## 将显卡借出

图像生成需要使用大部分显卡资源，而 vLLM 在运行时无法调整其内存大小。它在启动时预留资源，且不会减少。因此，设计上采用的是交换拥有者的方式，而不是分割资源池。

**一个记录器。** 每一分钟，一个根计时器会读取每个进程的 DRM fdinfo，其中 `xe` 驱动程序会报告每个客户端的 VRAM 使用情况和引擎忙碌时间。客户端通过其容器名称或命令名称来命名，因此每个 Plex Transcoder 进程都会被计为 `plex`。它会写入当前快照和一个每月的历史文件。历史文件还回答了一个开放性问题：Plex 在这张显卡上启用了硬件加速，并且有大量播放，但之前没有记录它实际进行转码的频率。

**一个仲裁器。** 一个小型服务维护一个照片请求队列和一个模式：`llm`、`swapping` 或 `image`。只有当队列不为空，vLLM 已经有 60 秒没有运行、等待或完成任何请求，并且记录器显示显卡上没有其他客户端时，它才会切换到 `image` 模式。然后它停止 vLLM，启动 ComfyUI 并加载 FLUX.1 Kontext，处理队列中的请求，一旦队列为空或 15 分钟已过，就将显卡交还。只有在 vLLM 通过健康检查后，它才会声明 `llm`。

**一个患者代理。** NanoClaw 代理通过一个小的代理与 vLLM 通信。它读取仲裁器的模式，并在模式不是 `llm` 时保持请求，同时重试被拒绝的连接。在交换过程中，如果代理需要发言，它会等待而不是失败。

第一天测量的结果：交换到 `image` 加上第一张照片耗时 85 秒，之后每张照片在 1328x800 和 24 步的情况下耗时 52 到 62 秒，而 vLLM 在交接后 56 秒内恢复健康。

## 未成功的工作

- **主线内核。** ELRepo 的 kernel-ml 能识别该显卡，但它是未签名的，而虚拟机启用了 Secure Boot。固件在用户空间之前就拒绝了它。即使使用自注册的机器所有者密钥进行签名，也无法启动。因此，它被移除了；这个虚拟机只运行 Red Hat 签名的内核。
- **Qwen3-32B。** 它看起来像是显存问题，重启了 252 次。内核日志显示不同：在 RSS 达到 8.3 GB 时，内存 cgroup 杀掉了进程，这正好是 compose 文件中设置的 `memory: 8G` 限制。下一次尝试时，限制提升到了 16GB。
- **原地调整大小。** 没有办法向正在运行的 vLLM 请求释放内存，而这正是仲裁器存在的全部原因。

## 前进的方向

计划是使用第二个 B70。两个显卡将在第二台机器中组成一个张量并行池（TP=2，64GB），因为当前主机是 Mini-ITX 板，只有一个 PCIe 插槽。Plex 和转码任务将转移到 Arc A380 显卡上。在此之前，对于任何共享的加速器，模式依然适用：在决定任何事情之前，先测量谁在使用它，当工作负载无法缩小的时候，应该交换整个显卡而不是分割使用它。
