DNS 和 DHCP 以前是在 nemesis 主机（主要的 Docker 主机）上的 Docker 容器中运行 Pi-hole，而 devastator 主机上运行了一个 Pi-hole，仅处理 DNS 请求。当承载该容器的主机宕机时，网络上的所有设备都无法解析名称，直到该主机恢复。

## 为什么是主机的问题

nemesis 是运行在 Proxmox 节点 sienar 上的一个虚拟机，它有崩溃的历史。在 8 月和 9 月期间，它记录了一系列带有不同签名的内核恐慌。崩溃转储显示，页面的映射指针与真实值仅相差一个位。结论是主机内存有问题，而该主机没有 ECC 内存，不是内核的错误。每次恐慌都需要 8 到 10 分钟的重启时间。

这次迁移早在 6 月就迫于另一种故障而进行。集群链路波动导致两个 Proxmox 节点分离，其中一个节点失去了 quorum 并卡住，不得不进行断电重启。在它宕机期间，整个网络都没有 DNS 服务。

## 双节点部署

现在 DNS 和 DHCP 在两个小型容器中运行，每个 Proxmox 节点上各一个：`dns-incomm` 和 `dns-sienar`。每个容器都是运行在特权模式下的 Debian 12 LXC，直接运行 Pi-hole v6，而不是在 Docker 中。keepalived 在它们之间维护一个虚拟地址。incomm 节点是主节点；如果它的 Pi-hole 停止响应，虚拟地址将转移到 sienar。

DHCP 也遵循相同的地址。keepalived 的通知脚本会在持有地址的节点上启用 DHCP，在另一个节点上禁用 DHCP，并且它只在实际状态变化时起作用，因此这两个节点不会同时分配 IP 地址。路由器本身的 DHCP 已关闭。客户端将共享地址作为其 DNS 服务器，因此故障切换对其一侧没有任何影响。

记录和保留仅在主节点上进行编辑。nebula-sync 会将它们复制到从节点。

旧的 Docker Pi-hole 容器在一段时间内保持运行，作为回滚的后备，之后被退役。

## 每个服务一个记录

内部 DNS 现在只使用一个通配符：homelab 域名下的所有名称都会解析到反向代理主机。一个新的 Web 服务只需要在代理上添加一个路由规则，无需其他操作：无需添加、忘记或遗留每个服务的记录。在外部网络中，这些名称通过公共 DNS 提供商解析。

Pi-hole v6 也会注册获取租约的机器的主机名，因此每台主机都会获得一个名称，而无需任何人手动记录。

## 仍然看似有效的机制

Docker 主机的仓库中仍然保留着一个 Ansible 剧本，它将 DNS 条目写入 `custom.list`，这是 Pi-hole v5 添加本地记录的方式。Pi-hole v6 则在 `pihole.toml` 的 `dns.hosts` 下保存这些记录，而它之前所针对的容器已经不存在了。这个剧本现在是一个无操作（no-op）。它不会失败；只是不发布任何内容。

曾经在那里添加过一个记录，看起来已经完成，但后来发现它无法被解析器访问，因此必须撤销。当服务迁移时，旧的更改方式必须被删除或明确标记，因为一个运行干净且不执行任何操作的机制看起来和一个正常工作的机制完全一样。

## 使用名称，而非地址

保存笔记库的桌面电脑有 DHCP 预留，因此它的地址应该永远不会改变。但地址两次发生了变化。6 月时，通过预留地址的 SSH 连接返回了 "No route to host"，而通过名称的相同连接却可以直接通过；名称跟随了机器的实际租约，而固定的地址已经过时。9 月时又发生了同样的情况，直接使用地址的 vault 同步操作静默失败。原因目前仍在调查中。

规则：通过名称访问主机。一个硬编码的地址只有在它背后的预留有效时才是可靠的，而当预留过期时，没有任何警告。

## 控制平面

DNS 对应的节点组成为了模板。现在有四个 LXCs 节点组，每个都绑定到物理节点上，而不是运行在可能崩溃的 VM 中：

- **控制节点：** tarkin 在 incomm（主节点）和 pellaeon 在 sienar（备用节点）上运行，承载 OpenTofu、Ansible 以及基础设施仓库的克隆。pellaeon 每十分钟拉取一次仓库。
- **DNS：** 上述的 Pi-hole 节点组。
- **运行状态监控：** 两个节点上都运行 Uptime Kuma。只有持有共享地址的节点会发送警报，其容器监控每两分钟与实际运行情况进行一次同步。
- **可观测性：** Prometheus 保留 30 天的数据，Grafana，以及一个包含两个成员的 Alertmanager 集群，通过 gossip 协议确保每个警报只在 Discord 中发送一次。导出器覆盖了主机、磁盘 SMART 数据以及 Proxmox API。

监控和可观测性主节点位于 sienar，这个节点配备了冗余电源；监控不应与被监控的对象共享相同的故障风险。舰队变更从 tarkin 通过基础设施仓库进行，而不是通过任意会话位置的临时 SSH 命令执行，因此每次变更都会被记录下来。

## 未成功的工作

- **第一次温度警报。** 它在传感器自身的“高”阈值上触发。标签因芯片而异：在 incomm 中，i7-12700K 的“高”温度为 80 C，这是其正常运行温度，因此它不断发出警报。现在规则在最热的核心上使用绝对阈值，95 C 时发出警告，98 C 时为严重。
- **然后警报是正确的。** incomm 在七月因热故障而硬崩溃，之后在约 11% 的 CPU 负载下运行温度在 92 到 100 C 之间。这是冷却问题，而不是负载问题，仍然需要硬件修复。
- **LXC 中的打包服务。** Pi-hole FTL、Prometheus 和 Grafana 提供了加固的 systemd 单元，它们在容器中启动前需要 drop-in。
- **Pi-hole 的配置仍然是声明式的。** 通配符和 keepalived 的设置在两个成员上都是手动应用的，尚未集成到 Ansible 中。

## 前进的方向

每一个新的核心服务都采用相同的结构：两个节点上的两个 LXC 容器，一个共享地址，一个写入器同步到另一个，以及由持有地址的成员发出警报。使用名称而不是地址，一个通配符覆盖多个记录，替换机制被移除，以防止它假装正常工作。
