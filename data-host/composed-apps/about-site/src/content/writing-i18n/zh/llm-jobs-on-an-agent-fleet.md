某些 LLM 的工作不应该在会话中进行：一百个摘要，一批分类，一个长期低风险的草稿，任何应保留在局域网中的私密内容。家庭实验室为此提供了一个小型服务。调用者提交一个提示和一个层级，会立即得到一个任务 ID，之后可以收集结果。这个服务现在已经构建了两次。

## 第一版：一个队列和一个网关

2026 年 6 月的版本在 nemesis 上运行，作为两个堆栈。 `llm-queue` 是一个 FastAPI 应用，包含一个 Web 仪表板、一个 REST API 和一个 MCP 端点，所有这些都使用一个 WAL 模式的 SQLite 数据库。调用者选择一个能力别名（在 B70 的 vLLM 上是 `fast`，在 CPU Ollama 上是 `background` 和 `reasoning`），每个别名都有自己的工作器，这样慢速的 CPU 任务不会阻塞 GPU 任务。

第二阶段在模型前面放置了一个 LiteLLM 网关。网关为每个用户颁发一个虚拟密钥，该密钥是所有地方的登录凭证：Web 界面、REST 和 MCP。队列将任务限定在密钥的哈希值上，并以该用户身份通过网关运行每个任务，因此配额只在一个地方管理。这意味着工作器在请求返回后需要调用者的密钥，因此每个任务行都携带了 Fernet 加密的密钥，工作器解密它，运行任务并在任务完成或取消后擦除它。LiteLLM 不会在 SQLite 中保存密钥，因此网关还需要一个 Postgres 侧车。

它有效，而且有很多复杂的机制。

## 它迁移到的舰队

九月，家庭实验室在 devastator 上部署了 NanoClaw 队列。NanoClaw 在容器中运行 Claude Code 代理，组织为代理组：每个组都有自己的指令、技能、挂载和环境，并且会为来自某个频道的消息或计划任务和一次性任务而唤醒。一些组直接与 Anthropic 通信。其他组则运行在 qwen3-14b 上，由本地 B70 上的 vLLM 提供服务，并通过一个小型的标准化代理进行访问，该代理使本地模型的 API 足够接近 Anthropic 的 API，以满足 Claude Code 的需求（它会折叠系统消息、限制输出令牌并关闭 qwen3 的思考模式）。

该队列已经完成了路由、访问控制和审计，这些是队列自己构建的功能。而且在 30 天内，没有任何东西使用过这个队列。

## 第二版：将任务作为代理任务

在 2026-09-19，队列和网关被从仓库中移除并停用。替代方案 `llm-jobs` 是一个基于 Python 标准库的服务，作为 systemd 用户单元在 devastator 上运行。它拥有两个东西：密钥和任务，都存储在一个 SQLite 文件中。其余一切均由 NanoClaw 处理。

任务的执行流程如下：

1. 调用者提交一个提示和一个层级。
2. 服务在该层级的代理组上创建一个一次性 NanoClaw 任务。
3. 该组的容器会唤醒，并在前面附加一个简短的工作者合同：只执行该任务，仅交付一次，不发布频道消息，不提问。
4. 代理通过 MCP 工具 `deliver_result` 向服务提交任务 ID 和其答案，或者如果任务无法执行，则提交一个错误信息。
5. 调用者轮询并获取结果。

Claude Code 会通过三个重要的 MCP 工具将其会话连接到该服务：`submit_job`、`get_status` 和 `get_result`（还有 `list_tiers`、`list_jobs` 和 `cancel_job`）。一个典型的调用看起来像这样：

```
submit_job(
  tier="local",
  prompt="Summarize the release notes below in five bullets for a homelab operator. <notes...>",
  params={"max_words": 150}
)
```

提示必须自包含；工作者看不到其他内容。`params` 的提示会变成工作者合同中的行。密钥是持有者密钥，按所有者范围限定：调用者只能看到自己的任务，结果保留 30 天。每个层级一次运行一个任务，如果任务在超时时间内没有交付，则任务失败并取消。

## 三个层级

- **local** 在 `jobs-local` 组上运行：通过代理运行 qwen3-14b，Anthropic 被阻止在容器中。免费且私有。一个简单的任务在 16 秒内返回。
- **claude** 在 `jobs-claude` 上运行：Sonnet，计费。一个简单的任务用了 50 秒。NanoClaw 没有每组使用上限，因此服务强制实施一个：每个密钥的每日上限，加上每个层级的每日任务和输出令牌上限，所有密钥共享。无论有多少密钥被使用，计费层级只有一个上限。
- **render**，于 2026-09-26 添加，在 `jobs-render` 上运行。提示是一个 JSON 配方（模型 URL、视图、样本、大小），该组具有 `blender-render` 技能和一个只读的 Blender 安装，并使用 Cycles 进行无头渲染静态图像。一个层级可以请求工件，这个层级会这样做：每个任务都会在容器中挂载自己的文件夹，`get_result` 列出文件，服务将它们提供给任务的所有者。如果配方中包含 `"photo": true`，工作者还会为每个视图调用 `request_photo` 并轮询 `photo_status`。这会在 devastator 上通过 GPU 调度器排队，当显卡空闲时，将从 vLLM 借出 B70 用于 FLUX Kontext 图像模型，并在每个渲染旁边生成一张照片。

工作者工具（`deliver_result`、`request_photo`、`photo_status`）仅对工作者可见。

## 未成功的内容

- **qwen3 无法通过代理驱动工具调用。** 普通文本任务在本地层级上运行。在代理后面，qwen3-14b 在工具调用回合中会失败，提示“内容块不是文本块”，而一个渲染任务仅仅是一些工具调用。渲染层级在 Sonnet 上运行，其有自己的小规模每日配额；一个渲染任务只需要其中几次调用。
- **代理容器中没有 GPU。** NanoClaw 没有设备直通功能，因此 Blender 在 CPU 上进行渲染，每个视图在 128 次采样下大约需要 35 秒。照片步骤只能获得 GPU，因为仲裁器在主机上运行，位于 NanoClaw 之外，而工作者通过 MCP 向其请求照片。

## 继续推进的内容

第二个版本更小，因为它不再拥有其他系统已经拥有的东西。作业服务保留密钥、作业、配额和工件；NanoClaw 保留模型、容器、技能和凭证。一个新的层级就是一个新的代理组，拥有自己的指令和技能，再加上层级表中的一条记录，这就是为什么一周后 Blender 渲染器可以到达，而调用者提交方式没有任何变化的原因。而且，每个层级的交付合同都是一样的：工作者调用一个工具，且仅调用一次，然后停止。
