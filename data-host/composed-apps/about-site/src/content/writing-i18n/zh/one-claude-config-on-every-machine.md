Claude Code 在 Windows 客户端、Linux 客户端和 RHEL 服务器上运行。每个都有一个全局 `CLAUDE.md`，一个 `settings.json`，一些技能和命令，而且每个都逐渐发展出略微不同的集合。旧的解决方法是手动复制，或者使用一个 Ansible 角色，当有人记得运行它时，将文件推送到其他机器。但这些方法都无法察觉在一台机器上做出的编辑，无法同步到其他机器。

## 技能的市场

Claude Code 可以从一个市场安装插件，而市场只是一个带有清单文件的 git 仓库，列出其中的插件。在 2026-09-18，一个私有仓库变成了市场。现在它列出了五个插件：

- **workshop**：网站上实体计划背后的 build-plan 和 shopcad-model 技能；
- **homelab-ops**：将 LLM 任务提交给家庭实验室舰队的技能；
- **gpu-llm**：一个技能加上一个 MCP 服务器，用于在游戏 GPU 上按需运行本地模型；
- **docs-tools**：Mermaid 图表和 Obsidian Markdown；
- **config-sync**：保持其他所有内容更新的插件。

大多数最初是 dotfiles 仓库中的松散技能。gpu-llm 插件只存在于一台机器上，且其提交从未被推送到远程仓库。它从该仓库的检出中被拉入市场，并被修改为通过 DNS 名称而不是已经漂移的 IP 地址来连接其主机。

## 两个真理来源

dotfiles 仓库是文件的真理来源：全局 `CLAUDE.md`、`settings.json`、非插件的技能以及命令。市场是插件的真理来源，插件的更改通过提升其版本号来发布。每个项目的内存、`settings.local.json`、凭证和缓存从不被修改。

## config-sync

2026-09-19 构建的 config-sync 插件是一个 bash 脚本和一个 `SessionStart` 钩子。每次会话开始时，它会对每个跟踪项进行哈希处理，并应用安全的操作。网络操作（快速前向 dotfiles 检出、更新市场、安装或更新它列出的每个插件）最多每 24 小时发生一次。当所有内容都同步时，它不会输出任何内容。当某些内容需要决策时，它会输出以 `config-sync:` 开头的行，而同一插件中的一个技能会告诉 Claude 如何读取和解决这些行。

使其安全的部分是一个小状态文件，其中保存了每个项目最后一次应用的哈希值。这将每个比较转换为一个三方比较：

- 仓库更新了，而本地副本没有更新：静默地应用更新；
- 本地副本更新了，而仓库没有更新：报告此情况，并且永远不会覆盖本地副本； `push` 会将更改带回仓库，这样其他机器可以获取到这些更改；
- 两者都更新了：报告冲突； `--force` 在 `apply` 或 `push` 上选择胜出者。

`settings.json` 作为 JSON 进行比较，忽略键的顺序，因此重新排序的文件不会被视为编辑。

脚本的表面很简单：

```
config-sync.sh status              # what differs, changes nothing
config-sync.sh apply [--force]     # pull, apply safe updates, update plugins
config-sync.sh push [-m msg]       # fold local edits back, commit, push
config-sync.sh diff <key>          # installed vs repo for one item
```

在新机器上，引导过程只有两行，注册市场并安装 config-sync，然后重启。第一个会话的钩子会克隆 dotfiles 仓库并安装全局配置和其他四个插件。Windows 下是在 Git Bash 中运行的。

测试使用一个临时的 home 和 dotfiles 仓库运行十五项检查，其中使用了模拟的 `claude` 二进制文件，并且没有网络连接。在第一台真正的机器上，`status` 将所有九个跟踪项都标记为已处于步骤中，而第一个 `push` 将全局 `CLAUDE.md` 的新部分带回了仓库。

## 后续的审查机器人

2026-09-24 添加了一个 GitHub Action，用于审查所有非草稿的拉取请求，在头部提交中添加批准或请求更改的结论，并合并干净的拉取请求。它只在头部未移动、没有 `no-automerge` 标签、并且工作流或插件目录下的内容没有更改时才进行合并。第一个版本使用 Claude 进行审查；同一天晚些时候，审查工作转移到了 NanoClaw 队列上的本地免费模型，以确保它们保留在局域网中。由于机器人不会合并对其自身工作流目录的更改，因此添加它的拉取请求需要人工进行合并。

## 未成功的工作

- **仅推送的 Ansible 角色。** 它作为后备方案保留，但推送配置无法看到远端所做的更改。在会话开始时拉取可以。
- **将插件写入到位。** Claude Code 的自动模式拒绝将脚本和钩子文件写入插件目录，将其标记为自我修改。将它们暂存到其他位置然后复制进去是允许的。审查机器人在它的合并脚本（“无需审查的合并”）上遇到了同样的问题，只有在所有者在自动模式之外批准后才被编写。
- **在 `/tmp` 中的测试桩。** `/tmp` 挂载在主服务器的 `noexec` 上，因此放置在那里的桩二进制文件会被静默跳过，实际的程序会运行。对于 config-sync，桩现在通过 `sh` 运行。对于审查机器人，测试达到了真正的 GitHub CLI，得到了 422 错误，并且没有发布任何内容；现在 `gh` 被作为 shell 函数进行桩处理。

## 延续的内容

现在全局编辑只有一条路径：在任意机器上进行修改，`push`，其余部分将在下次会话启动时进行收敛。一个新的被跟踪的文件是脚本中的一种情况和版本号的提升。dotfiles 仓库中那些已移动到插件中的技能的副本仍然存在，并且在每台机器运行 config-sync 时会再次出现。
