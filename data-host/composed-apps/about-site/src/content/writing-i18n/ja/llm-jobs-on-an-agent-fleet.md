LLMの一部の作業は、セッションとして扱うべきではない。100の要約、分類のバッチ、長くても低リスクの下書き、LAN上に残るべきプライベートな内容などである。ホームラボには、このような作業を処理するための小さなサービスがある。呼び出し元はプロンプトと階層を送信し、すぐにジョブIDを受け取り、後で結果を収集する。このサービスはすでに2回構築された。

## バージョン1: キューとゲートウェイ

2026年6月のバージョンは、nemesis上に2つのスタックとして実行されていた。`llm-queue`は、FastAPIアプリで、Webダッシュボード、REST API、MCPエンドポイントを1つのWALモードのSQLiteデータベース上で提供していた。呼び出し元は、能力のエイリアス（B70のvLLM上の`fast`、CPU Ollama上の`background`と`reasoning`）を選択し、それぞれのエイリアスには独自のワーカーが存在したため、遅いCPUジョブがGPUジョブを妨げること never なかった。

2段階目では、モデルの前にLiteLLMゲートウェイを配置した。ゲートウェイは、各ユーザーに仮想キーを発行し、そのキーがすべての場所でログインに使用された。キューは、キーのハッシュに基づいてジョブをスコープ化し、ゲートウェイを通じてそのユーザーとしてすべてのジョブを実行したため、クォータは1箇所に管理された。つまり、ワーカーは、リクエストが返却された後に呼び出し元のキーが必要となったため、各ジョブ行はFernetで暗号化されたキーを保持し、ワーカーはそれを復号化し、ジョブを実行し、ジョブが完了またはキャンセルされた後に情報を削除した。LiteLLMはSQLiteにキーを保持しないため、ゲートウェイにはPostgreSQLのサイドカーも必要だった。

これは動作し、多くの機械仕掛けを必要とした。

## それが動かした艦隊

9月、homelabはdevastatorにNanoClawの艦隊を導入しました。NanoClawは、コンテナ内でClaude Codeエージェントを実行し、エージェントグループとして組織されています。各グループは独自の指示、スキル、マウント、環境を持ち、特定のチャンネルからのメッセージ、またはスケジュールされたタスクや一時的なタスクのためだけに起動します。一部のグループはAnthropicと直接通信します。他のグループは、ローカルのB70でvLLMによって提供されるqwen3-14b上で実行され、AnthropicのAPIとある程度似た挙動を示す小さな正規化プロキシを通じてアクセスされます（このプロキシは、システムメッセージを折り畳み、出力トークンを制限し、qwen3の思考モードを無効にします）。

この艦隊は、すでにキューが自ら構築したルーティング、アクセス制御、および監査を担当していました。そして、このキューは30日間使用されていませんでした。

## バージョン2: ジョブをエージェントタスクとして

2026年9月19日、キューとゲートウェイは削除され、リポジトリから取り除かれました。代替として、`llm-jobs`はdevastator上でsystemdユーザー単位として実行されるPython標準ライブラリサービスです。このサービスは、鍵とジョブの2つの要素を1つのSQLiteファイルに保存しています。それ以外のすべてはNanoClawです。

ジョブの流れは以下の通りです:

1. 呼び出し元がプロンプトと階層を送信します。
2. サービスは、その階層のエージェントグループで一時的なNanoClawタスクを作成します。
3. グループのコンテナは、短いワーカー契約を先頭に付けて起動します: ジョブを正確に実行し、1回だけ結果を返し、チャンネル投稿や質問は行いません。
4. エージェントは、ジョブIDとその回答、またはジョブが実行できない場合のエラーメッセージを含むサービスのMCPツール`deliver_result`を呼び出します。
5. 呼び出し元はポーリングを行い、結果を取得します。

Claude Codeセッションは、3つの重要なツールを持つMCPサーバーとしてこのサービスにアクセスします: `submit_job`、`get_status`、`get_result`（さらに`list_tiers`、`list_jobs`、`cancel_job`もあります）。典型的な呼び出しは以下のようになります:

```
submit_job(
  tier="local",
  prompt="Summarize the release notes below in five bullets for a homelab operator. <notes...>",
  params={"max_words": 150}
)
```

プロンプトは自己完結型でなければなりません。ワーカーはそれ以外の情報を何も見ません。`params`のヒントは、ワーカー契約の行になります。キーはベアラー・キーであり、所有者ごとにスコープが設定されています。呼び出し元は自分のみのジョブを確認でき、結果は30日間保持されます。1つのティアに1つのジョブが同時に実行され、タイムアウト内に配信がない場合は、そのジョブは失敗とされ、タスクはキャンセルされます。

## 3つのティア

- **local** は `jobs-local` グループ上で実行されます: qwen3-14b はプロキシを通じて実行され、Anthropic はコンテナからブロックされています。無料でプライベートです。簡単なジョブは16秒で戻ってきました。
- **claude** は `jobs-claude` 上で実行されます: Sonnet、メータリング済み。簡単なジョブは50秒かかりました。NanoClaw にはグループごとの使用量上限はありませんので、サービスは1つ設定しています: キーごとの日次上限、およびすべてのキーが共有するティア全体の日次上限（ジョブ数と出力トークン数）。どのくらいのキーが存在しても、メータリングされたティアには1つの上限があります。
- **render** は 2026-09-26 に追加され、`jobs-render` 上で実行されます。プロンプトは JSON レシピ（モデルURL、ビュー、サンプル、サイズ）です。グループには `blender-render` スキルと読み取り専用の Blender インストールがあり、Cycles を使用してヘッドレスで静止画をレンダリングします。ティアはアーティファクトを要求できます。このティアはそうしています: 各ジョブはコンテナにマウントされた独自のフォルダを取得し、`get_result` はファイルを一覧表示し、サービスはそれらをジョブの所有者に提供します。レシピに `"photo": true` が含まれている場合、ワーカーは `request_photo` を各ビューに対して呼び出し、`photo_status` をポーリングします。それにより、devastator 上の GPU アービタにパスがキューイングされ、カードが空いているときに vLLM から B70 を FLUX Kontext 画像モデルに貸し出し、各レンダリングの隣に写真を保存します。

ワーカー・ツール（`deliver_result`、`request_photo`、`photo_status`）はワーカーのみに表示されます。

## うまくいかなかったこと

- **qwen3はプロキシを通じてツールコールを実行できません。** プレーンテキストのジョブはローカル層で動作します。プロキシの後ろでは、qwen3-14bはツールコールのターンで「Content block is not a text block」というエラーになり、レンダリングジョブはツールコール以外のものではありません。レンダリング層はSonnetで実行され、独自の小さな日次上限があります。レンダリングジョブには、それらのコールを数回行うだけで済みます。
- **エージェントコンテナにGPUがありません。** NanoClawにはデバイスパススルーがありませんので、BlenderはCPUでレンダリングを行い、128サンプルあたり約35秒かかります。写真のステップではGPUが使用できるのは、アービターがNanoClawの外側、ホスト上に実行されているため、ワーカーはMCPを通じてアービターに写真を依頼するからです。

## 進化した点

2バージョン目は、もう1つのシステムがすでに所有していたものを所有しなくなったため、サイズが小さくなっています。ジョブサービスは鍵、ジョブ、上限、アーテファクトを保持し、NanoClawはモデル、コンテナ、スキル、資格情報を保持します。新しい層は、独自の指示とスキルを持つ新しいエージェントグループ、および層テーブルに1つのエントリを追加することによって実現されます。このように、呼び出し元がどのように送信するかを変更することなく、1週間後にBlenderレンダラーが到着しました。そして、すべての層で配信契約は同じです：ワーカーは1つのツールを1回だけ呼び出し、その後終了します。
