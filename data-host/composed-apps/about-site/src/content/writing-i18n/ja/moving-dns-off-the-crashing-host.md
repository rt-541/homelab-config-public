DNS と DHCP は、メインの Docker ホストである nemesis 上で Docker を使用した Pi-hole として実行されていました。また、devastator というホスト上には、DNS のみを処理する 2 番目の Pi-hole がありました。そのコンテナを実行していたホストが停止すると、ネットワーク上のすべてのデバイスが名前解決ができなくなり、再び起動するまで名前を解決できませんでした。

## なぜホストが問題だったのか

nemesis は Proxmox ノード sienar 上の仮想マシンであり、クラッシュの歴史がある。8月と9月にかけて、異なる署名を持つカーネルパニックの連続を記録している。クラッシュダンプの分析では、ページのマッピングポインタが実際の値からちょうど1ビットだけずれていることが確認された。結論としては、ECCを備えていないホストの不安定なメモリの問題であり、カーネルのバグではなかった。各パニックは、再起動に8から10分かかる。

この移動は、6月に別の障害によって強制された。クラスターリンクのフラップにより、2つの Proxmox ノードが分離され、1つはクォーラムを失い、停止してしまった。そのノードは電源を再投入する必要があった。その間、どこにもDNSは存在しなかった。

## ペア

DNS と DHCP は今や、2つの小さなコンテナで動作しており、それぞれ Proxmox ノードの1つに配置されています: `dns-incomm` と `dns-sienar`。それぞれは特権付きの Debian 12 LXC で、Docker ではなく Pi-hole v6 をネイティブに実行しています。keepalived は、この2つのノードの間で仮想アドレスを保持しています。incomm メンバーがマスターであり、もし Pi-hole が応答しなくなると、アドレスは sienar に移動します。

DHCP も同じアドレスを追跡します。keepalived の notify スクリプトは、仮想アドレスを保持しているメンバーで DHCP を有効にし、もう一方のメンバーでは無効にします。これは、実際の状態変化にのみ反応するため、2つのノードが同時にリースを配布することはありません。ルーター自身の DHCP は無効になっています。クライアントは、共有アドレスを DNS サーバーとして設定しているため、フェールオーバーが発生してもクライアント側に変更は必要ありません。

レコードや予約はプライマリノードでのみ編集されます。nebula-sync はそれらをセカンダリノードにコピーします。

古い Docker 上の Pi-hole は、ロールバック用に一定期間稼働させた後、廃止されました。

## サービスごとに1つのレコード

内部 DNS は現在、単一のワイルドカードを採用しています。homelab のドメインの下にあるすべての名前は、リバースプロキシのホストに解決されます。新しい Web サービスは、プロキシにルーティングルールを設定するだけで済み、それ以外の処理は必要ありません。各サービスごとのレコードを追加したり、忘れたり、後回しにしたりする必要がありません。ネットワークの外側では、同じ名前はパブリック DNS プロバイダを通じて解決されます。

Pi-hole v6 は、リースを取得する機械のホスト名を登録するため、各ホストが名前を持つように自動的に設定されます。これにより、誰も名前を手動で記録する必要がありません。

## まだ生きているように見えたメカニズム

Docker-host レポジトリには、まだ Ansible playbook が含まれており、これは `custom.list` に DNS エントリを書き込むという、Pi-hole v5 におけるローカルレコードの追加方法です。Pi-hole v6 では、これらは `pihole.toml` の下の `dns.hosts` に保存され、以前にターゲットにしていたコンテナはもはや存在しません。この playbook は、何の処理も行いません。失敗することはありません。ただ、何も公開しません。

かつてその場所にレコードを追加し、完了したように見えたものの、最終的にどのリゾルバにも到達できないことが判明し、戻す必要がありました。サービスが移動した場合、古い方法で変更を加えることは削除するか、明確にマークする必要があります。なぜなら、何も処理を行わないクリーンなメカニズムは、実際に動作しているように見えるからです。

## 名前、住所ではなく

ノートのボックスを保持しているデスクトップにはDHCPの予約が設定されており、そのIPアドレスは決して変更されないはずでした。しかし、2回その予約が変更されました。6月には、予約されたアドレスにSSH接続を試みると「No route to host」というエラーが返されましたが、同じ接続を名前で行うと問題なく通りました。この場合、名前はマシンの実際のリースに従っており、固定されたアドレスは古くなっていたのです。9月にも同様のことが再発し、アドレスを直接使用して行われていたボックスの同期は静かに失敗しました。原因はまだ特定されていません。

ルール：ホストは名前でアクセスする。ハードコードされたアドレスは、その背後にある予約の信頼性だけしか保証できず、それが古くなったときに警告するものはありません。

## コントロールプレーン

DNSペアはテンプレートとなりました。現在、4つのLXCペアがあります。これらはすべて、仮想マシン（VM）ではなく、物理ノードにピン留めされています。VMはクラッシュする可能性があるためです。

- **制御:** incomm上のtarkin（プライマリ）とsienar上のpellaeon（フェイルオーバー）が担当しています。OpenTofu、Ansible、およびインフラストラクチャリポジトリのクローンを保持しています。pellaeonは10分ごとにリポジトリをプルします。
- **DNS:** 上記のPi-holeペア。
- **稼働時間監視:** 両方のノードにUptime Kumaがインストールされています。共有アドレスを持つノードのみがアラートを送信し、そのコンテナの監視は実際の稼働状況と2分ごとに整合性が取られます。
- **観測性:** Prometheus（30日間の保持期間）、Grafana、および2ノード構成のAlertmanagerクラスタ（gossip通信により、アラートがDiscordに1回だけ届くように設計）。エクスポータはホスト、ディスクSMARTデータ、およびProxmox APIをカバーしています。

監視および観測性のマスターは、冗長電源を持つsienarノード上に配置されています。監視対象と監視者とは運命を共有してはいけません。Fleetの変更は、インフラストラクチャリポジトリからtarkinから実行され、セッションがどこであれ、即席のSSHによる変更ではなく、すべての変更は記録されます。

## うまくいかなかったこと

- **最初の温度アラート。** これはセンサー独自の「high」しきい値で発火しました。ラベルはチップごとに異なります: incomm に使われている i7-12700K では 80 C が「high」と表示され、これは通常の動作温度なので、アラートが頻繁に発生しました。現在のルールでは、最も高温のコアに絶対しきい値を適用しており、95 C で警告、98 C で重大な問題と判定しています。
- **その後アラートは正しいものでした。** incomm は7月に熱故障によりハングしました。その後、約11％のCPU負荷で92〜100 Cで動作していました。これは冷却不良によるものであり、負荷ではなく、ハードウェアの修正が必要です。
- **LXCでのパッケージ化されたサービス。** Pi-hole FTL、Prometheus、Grafana は、コンテナで起動する前に drop-in が必要な強化された systemd ユニットを提供しています。
- **Pi-holeの設定は依然として命令型です。** ワイルドカードと keepalived の設定は、両方のノードで手動で適用されており、Ansible にはまだ含まれていません。

## 何が引き継がれるか

すべての新しいコアサービスは同じ構造になります：2つのLXCを2つのノード上に配置し、1つの共有アドレス、1つのライターがもう1つと同期し、アドレスを持つメンバーからアラートが送られます。名前をアドレスに置き換え、1つのワイルドカードを多くのレコードに代えて、置き換えられたメカニズムは削除され、動作しているように偽装することはできません。
