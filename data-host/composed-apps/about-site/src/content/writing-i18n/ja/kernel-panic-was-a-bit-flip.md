ホームラボの主要な Docker ホストは nemesis で、これは Proxmox ホスト sienar 上の RHEL 9 仮想マシンです。nemesis がパニックを起こすと、その背後にあるすべてのサイトが kdump が完了し、仮想マシンが再起動するまでダウンします。毎回約10分かかります。今年の夏は頻繁にパニックを起こしました。

## カーネルを指し示すパターン

8月の最初の2週間で、あるカーネル構築に対して9回のパニックが発生し、そのうち7回は `kswapd0` 内部のカーネルのページ再確保スレッドにおける NULL ポインタの dereference でした。これは明らかにカーネルのバグを示しており、明確な対処法はカーネルの更新でした。更新は8月24日に適用され、ホストは6日間パニックを起こさなかったように見えました。

その後、新しいカーネル上で3回のイベントが発生しました：

- **8月30日:** ヘッドレスブラウザのスレッドに関連する "stack-protector: Kernel stack is corrupted in futex_parse_waitv" というパニック。
- **9月12日:** 資格情報の解放中に `refcount_t: underflow; use-after-free` の警告。
- **9月13日:** `kswapd0` の Oops、今回はマルチジェネレーション LRU (MGLRU) 再確保コードから到達したスピンロックのスロウパスにおける悪いページフォルト。

メモリの圧力がトリガーではなかったことがわかりました。仮想マシンの使用率は22%で、スワップはアイドル状態でした。kswapd は常に実行されているのは、ページキャッシュが常に仮想マシンを埋め尽くすためで、それによりページを多く触れているため、破損したページに出会う可能性が最も高いコードです。

2週間以内に、関係のないサブシステムで3つの破損のサインが確認されたのは、1つのカーネルのバグとは見えません。

## vmcore が語ったこと

`crash` とマッチする `kernel-debuginfo` を使用して、9月13日のダンプを手動で解析することが可能でした。再確保は `folio->mapping->host` を通してロックを取得しており、そのロックのアドレスは dentry スラブ内にありました。folio から戻る経路をたどると：

```
folio->mapping (observed)   ffff89417d547db0
real i_data of that inode   ffff89417d547df0
difference                  0x40, one bit
```

観測されたポインタは、メディアアレイ上の19GBの映画が含まれるライブXFSのinode内にあり、そのスラブレイアウトのinodeの`i_data`であることはできないため、破損しているが、陳腐化しているわけではない。`struct page`の1ビットが反転していた。

8月30日のダンプも同意している。スタックプロテクターが発火しており、ダンプ時のスタック、タスク、およびper-CPUのカナリーはすべて同じ値だった。比較は一度間違った値を読み取った。

下層のハードウェアがその理由を説明している。sienarはX299ボードで、i7-7820Xと非ECCメモリ（カーネルログによると`EDAC skx: ECC is disabled on imc 0`）を搭載しており、KSM（Kernel Samepage Merging）がゲスト間で同一のページをマージする状態で動作していた。主な仮説は、RHELカーネルのバグではなく、ホストメモリまたはCPUの不安定性であると考えられるようになった。

## 次の日

9月14日に、同じような不安定性がユーザースペースでも現れた。dockerdはGoランタイムの致命的なエラー（`found pointer to free object`）とともに死んだ。これは、ヒープの破損を検出するゴミ収集器の動作である。再起動されたデーモンは、すべての孤立したコンテナを終了させた。21のコンポーズプロジェクトにまたがって49のコンテナが終了し、エッジプロキシ、このサイト、メディアスタック、Discordボットも含まれていた。

`restart: unless-stopped`はその中からちょうど1つだけを復元した。

## その代償

- **暗黙のホストの約10時間**。朝から夕方まで。
- **見逃された uptime モニタ**。このモニタは動的にコンテナチェックを構築しており、実行されていないコンテナのチェックはドロップするため、大規模な停止は監視数が減ったように見えるだけで、赤い監視とはならない。静的なチェックは5つだけが赤くなった。
- **4週間もダウンしていたストラグラー**。9月13日のパニックの後、8月のクラッシュからまだ`Exited (255)`状態だったサービスが1つ見つかった。再起動ポリシーやautoheal（実行中の不健全なコンテナのみを再起動する）はその状態に気づかなかった。

復旧は手動でした: 各プロジェクトは、コンテナのコンポーズラベルに記載されたディレクトリから `docker compose up -d` で復元されました。

## 変更点

- **起動時にストラグラーを復活させる。** `scripts/revive-stragglers.sh` は、コード 255 で終了し、再起動ポリシーが `always` または `unless-stopped` であり、コンポーズで管理されているコンテナを検出し、それらのサービスを自身のディレクトリから `docker compose up -d` を実行します。意図的に停止されたスタックは他のコードで終了し、無視されます。systemd ユニットは、Docker が起動した後 2 分後にこれを実行します。
- **live-restore が設定されている。** Docker の `live-restore` 設定により、デーモンの再起動時にもコンテナが実行状態を維持します。そのため、次の dockerd のクラッシュでもコンテナが一緒にダウンすることはないはずです。この設定はデーモンの設定に含まれており、次のデーモンの再読み込み時に有効になります。
- **sienar では KSM がオフになっているため、1 ページの翻訳は他のゲストに共有できません。**
- **リポジトリで MGLRU スイッチが切り替わった。** tmpfiles.d のエントリにより、MGLRU の回収が無効になります:

```
  w /sys/kernel/mm/lru_gen/enabled - - - - n
  ```

この変更はまだ適用されておらず、RCA はこれをオプションとしてマークしています: 2 回トリップしたコードパスを削除しますが、次の翻訳は別の場所に落ちるだけです。
- **vmcore の削除。** 7 月下旬から、tmpfiles.d のルールにより、14 日以上前の kdump ダンプが削除されるため、パニックの連続が 20 GB の `/var` ボリュームを埋めることはありません（各ダンプは約 1 GB です）。
- **リポジトリ内に RCA が含まれており、ダンプテーブルも含まれています。**

## 未解決の問題

- nemesis VM を数週間間、別の Proxmox ノードに移動して A/B テストとして実施します。パニックがそこで止まる場合、sienar が原因です。
- メンテナンスウィンドウ中に sienar で memtest86+ を実行します。
- 実行中のコンテナ数を監視する機能を追加し、各コンテナのチェックが消えても、大規模な停止が見えるようにします。

## 今後も継続する内容

カーネル関数内で同じ場所にクラッシュが繰り返されることが、必ずしもカーネルのバグを示すわけではない。これは、その関数が最も多くのメモリにアクセスしていることを示している可能性もある。同じマシン上で関係のないコードで異なるサインチャーナーが発生する場合、それはソフトウェアの下層、つまりハードウェアやオペレーティングシステムの問題を示唆している。クラッシュダンプとデバッグシンボルがあれば、その仮説を1ビットの差分にまで絞り込むことができる。Dockerの観点から見れば、再起動ポリシーは不完全なクラッシュ後の回復計画ではない。また、動作中のみを監視するモニタは、何が停止したかを報告することはできない。
