일부 LLM 작업은 세션에서 처리되어서는 안 된다: 수십 개의 요약, 일괄 분류, 긴 낮은 위험도 초안, LAN에 남아야 할 개인 정보 등이다. 홈 랩에는 그런 작업을 처리할 수 있는 작은 서비스가 있다. 호출자는 프롬프트와 계층을 제출하면, 즉시 작업 ID를 받고 나중에 결과를 수집한다. 이 서비스는 두 번 만들어졌다.

## 첫 번째 버전: 대기열과 게이트웨이

2026년 6월 버전은 nemesis에서 두 개의 스택으로 실행되었다. `llm-queue`은 WAL 모드의 하나의 SQLite 데이터베이스 위에 웹 대시보드, REST API 및 MCP 엔드포인트를 갖춘 FastAPI 앱이었다. 호출자는 B70의 vLLM에서 `fast`, CPU Ollama에서 `background` 및 `reasoning`과 같은 능력 별칭을 선택했으며, 각 별칭은 자체 워커를 가졌기 때문에 느린 CPU 작업이 GPU 작업을 차단하지 않았다.

두 번째 단계에서는 모델 앞에 LiteLLM 게이트웨이를 배치했다. 게이트웨이는 각 사용자에게 가상 키를 발급했으며, 이 키는 모든 곳에서 로그인에 사용되었다: 웹 UI, REST 및 MCP. 대기열은 키의 해시에 따라 작업을 범위 지정했으며, 모든 작업은 해당 사용자로 게이트웨이를 통해 실행되었기 때문에 할당량은 한 곳에서 관리되었다. 이는 워커가 요청이 반환된 후 호출자의 키가 필요하게 되었음을 의미했으며, 따라서 각 작업 행은 키를 Fernet 암호화하여 저장했고, 워커는 이를 해독하여 작업을 실행하고 작업이 완료되거나 취소되면 이를 정리했다. LiteLLM은 SQLite에 키를 보관하지 않기 때문에 게이트웨이에는 Postgres 사이드카도 필요했다.

이것은 작동했으며, 많은 장비가 필요했다.

## 이 서비스가 이전한 플랫폼

9월에 homelab은 devastator에 NanoClaw 대규모 편대를 추가했습니다. NanoClaw는 컨테이너에서 Claude Code 에이전트를 실행하며, 에이전트 그룹으로 구성됩니다. 각 그룹은 자체 지시사항, 자체 기술, 자체 마운트 및 환경을 가지며, 특정 채널에서 메시지를 받거나 예약 및 단일 작업을 위해 활성화됩니다. 일부 그룹은 Anthropic과 직접 통신합니다. 다른 그룹은 로컬 B70에서 vLLM을 통해 제공되는 qwen3-14b 모델에서 실행되며, 이는 작은 정규화 프록시를 통해 로컬 모델의 API가 Anthropic의 API와 충분히 유사하게 작동하도록 합니다(시스템 메시지를 접합하고 출력 토큰 수를 제한하며 qwen3의 사고 모드를 비활성화합니다).

이 편대는 이미 큐가 자체적으로 구축한 라우팅, 접근 제어 및 감사를 수행해 왔습니다. 그리고 30일 동안 아무것도 큐를 사용하지 않았습니다.

## 두 번째 버전: 작업을 에이전트 작업으로

2026-09-19에 큐와 게이트웨이는 구성되어 제거되고 저장소에서 제거되었습니다. 대체품인 `llm-jobs`은 Python 표준 라이브러리 서비스로, devastator에서 systemd 사용자 유닛으로 실행됩니다. 이 서비스는 키와 작업 두 가지를 소유하며, 모두 하나의 SQLite 파일에 저장됩니다. 나머지는 모두 NanoClaw입니다.

작업의 흐름은 다음과 같습니다:

1. 호출자는 프롬프트와 계층을 제출합니다.
2. 서비스는 해당 계층의 에이전트 그룹에서 단일 작업용 NanoClaw 작업을 생성합니다.
3. 그룹의 컨테이너는 짧은 작업자 계약을 앞에 추가하여 활성화됩니다: 작업을 정확히 수행하고, 한 번만 결과를 전달하며, 채널 게시물이나 질문은 하지 않습니다.
4. 에이전트는 작업 ID와 답변을 서비스의 MCP 도구 `deliver_result`에 전달하거나, 작업을 수행할 수 없는 경우 오류 문장을 전달합니다.
5. 호출자는 결과를 확인하고 가져옵니다.

Claude Code 세션은 `submit_job`, `get_status` 및 `get_result`(또한 `list_tiers`, `list_jobs` 및 `cancel_job`)의 세 가지 도구가 있는 MCP 서버로 접근합니다. 일반적인 호출 예시는 다음과 같습니다:

```
submit_job(
  tier="local",
  prompt="Summarize the release notes below in five bullets for a homelab operator. <notes...>",
  params={"max_words": 150}
)
```

프롬프트는 자체적으로 완전해야 합니다; 워커는 다른 것을 보지 못합니다. `params`의 힌트는 워커 계약의 줄이 됩니다. 키는 베어어 키이며, 소유자별로 범위가 지정됩니다: 호출자는 자신의 작업만 볼 수 있으며, 결과는 30일 동안 보관됩니다. 한 계층당 한 번에 하나의 작업이 실행되며, 시간 초과 내에 전달이 없는 작업은 실패하고 작업이 취소됩니다.

## 세 계층

- **local**은 `jobs-local` 그룹에서 실행됩니다: qwen3-14b는 프록시를 통해 실행되며, Anthropic는 컨테이너에서 차단됩니다. 무료 및 개인적입니다. 간단한 작업은 16초 만에 돌아왔습니다.
- **claude**는 `jobs-claude`에서 실행됩니다: Sonnet, 체크된 사용량. 간단한 작업은 50초 소요되었습니다. NanoClaw는 그룹별 사용량 제한이 없기 때문에 서비스는 하나를 강제로 적용합니다: 키별 일일 사용량 한도, 그리고 모든 키가 공유하는 계층 전체의 일일 작업 및 출력 토큰 한도. 키가 몇 개든, 체크된 계층은 하나의 한도만 가지고 있습니다.
- **render**, 2026-09-26에 추가되었습니다, `jobs-render`에서 실행됩니다. 프롬프트는 JSON 레시피(모델 URL, 뷰, 샘플, 크기)입니다. 그룹에는 `blender-render` 기술과 읽기 전용 Blender 설치가 있으며, Cycles를 사용하여 헤드리스로 정지 이미지를 렌더링합니다. 계층은 아티팩트를 요청할 수 있으며, 이 계층은 그렇게 합니다: 각 작업은 컨테이너에 마운트된 고유한 폴더를 가지며, `get_result`는 파일을 나열하고, 서비스는 해당 작업의 소유자에게 이를 제공합니다. 레시피에 `"photo": true`이 포함되어 있다면, 워커는 각 뷰에 대해 `request_photo`을 호출하고 `photo_status`을 확인합니다. 이는 devastator의 GPU 관리자에서 한 번의 요청을 줄이며, 카드가 유휴 상태일 때 vLLM의 B70을 FLUX Kontext 이미지 모델에 빌려주고, 각 렌더링 옆에 사진을 작성합니다.

워커 도구(`deliver_result`, `request_photo`, `photo_status`)는 워커에게만 보입니다.

## 작동하지 않은 사항

- **qwen3는 프록시를 통해 툴 호출을 실행할 수 없습니다.** 일반 텍스트 작업은 로컬 계층에서 실행됩니다. 프록시 뒤에서 qwen3-14b는 툴 호출 단계에서 "Content block is not a text block" 오류가 발생하며, 렌더 작업은 툴 호출뿐입니다. 렌더 계층은 Sonnet에서 실행되며, 자체의 작은 일일 제한 내에서 작동합니다. 렌더 작업은 그 호출 중 몇 개만 필요합니다.
- **에이전트 컨테이너에 GPU가 없습니다.** NanoClaw에는 장치 전달이 없기 때문에 Blender는 CPU에서 렌더링되며, 128 샘플 기준으로 한 뷰당 약 35초가 소요됩니다. 사진 단계에서만 GPU가 사용되는 이유는 중재자(arbiter)가 호스트에서 NanoClaw 외부에 실행되고, 워커가 MCP를 통해 사진을 요청하기 때문입니다.

## 이어나가는 요소

두 번째 버전은 다른 시스템이 이미 소유하고 있던 것을 더 이상 소유하지 않기 때문에 더 작아졌습니다. 작업 서비스는 키, 작업, 제한 및 아티팩트를 유지하고, NanoClaw는 모델, 컨테이너, 기술 및 자격 증명을 유지합니다. 새로운 계층은 각각의 지시 및 기술을 가진 새로운 에이전트 그룹과, 계층 테이블에 하나의 항목을 추가하는 것입니다. 이로 인해 한 주 후 Blender 렌더러가 호출자들이 제출하는 방식에 어떤 변경도 없이 도착할 수 있었습니다. 그리고 모든 계층에 대한 배송 계약은 동일합니다: 워커는 하나의 툴을 정확히 한 번 호출하고 멈춥니다.
