# Fix `data_lvm_2.5ssd1` Storage Pressure (sienar) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. This plan TOUCHES a running production VM's disks — read the **Safety** notes on every step before acting. The investigation that produced the Findings was read-only; nothing on the infra was changed.

**Goal:** Drain `data_lvm_2.5ssd1` (currently 99.59% full, the cause of the `PveStorageHigh` alert) down to a safe utilization (target ≤ 80%) by relocating one of VM 100's two thick disks onto a pool that has free space, without data loss and with the minimum guest downtime.

**Architecture / situation:** `data_lvm_2.5ssd1` is a **thick** `lvm` storage (not a thin pool) sitting on a single 512 GB SATA SSD (`/dev/sda`, SK hynix SH920, 476.94 GiB usable) on PVE node **sienar**. Because it is thick, every allocated LV consumes its full nominal size on disk — there is no overcommit headroom to reclaim. The VG has only **~1.94 GiB free**. The only consumer is **VM 100 ("nemesis")**, which holds two thick volumes there. Relief therefore means moving (at least) one of those two disks off `/dev/sda` onto a pool with room.

**Tech Stack:** Proxmox VE 8.4.19 (kernel 6.8.12-29-pve), LVM/LVM-thin, `qm move-disk` for online/offline disk relocation, `pvesm` for storage status.

**Access / conventions:** PVE hosts via `ssh -o IdentitiesOnly=yes lo204@192.168.1.5` (sienar), passwordless `sudo -n` for `pvesm`/`lvs`/`qm`. `/etc/pve` is cluster-shared. homelab-config repo commit branch `main`, `sudo docker compose` (n/a here — this is PVE-side work). Do **not** `git add -A`; the repo has unrelated dirty files.

### Can the underlying disk grow? — No (cheap path).

`/dev/sda` is a single physical 512 GB SK hynix SATA SSD; `pvs` shows the PV `<476.94g` with only `<1.94g` free, and `lsblk` confirms the disk is fully consumed by the VG. There is **no unpartitioned tail** to `pvresize` into and the VG is a single-PV VG. Growing it would require physically replacing the SSD with a larger one (offline, `dd`/`pvmove` dance) — out of scope as a first response. Adding a second PV to the VG is possible (LVM supports multi-PV VGs) but there is no spare SATA SSD free; every other disk is already in `data_lvm_raid`, `data_lvm_raid2`, `data_lvmt_m2`, or `pve`.

## Options

### Option A — Move one VM 100 disk off `data_lvm_2.5ssd1` to `data_lvmt_m2` (RECOMMENDED)

Use `qm move-disk` to relocate **`scsi3` (the 175 GiB cache disk)** from `data_lvm_2.5ssd1` to the `data_lvmt_m2` thin pool, which has ~722 GiB free. `qm move-disk` on a **running** VM performs a live block mirror (drive-mirror) and is **online / zero-downtime**.

- Frees **175 GiB** on `/dev/sda` → `data_lvm_2.5ssd1` drops from 99.59% to roughly **(498073600 − 175·1048576) / 500105216 ≈ 63%** used. Comfortably under the 80% alert threshold.
- Moving the **cache** disk (scsi3) rather than the **boot** disk (scsi0) is preferred: it is not the boot device, so even if we elected a downtime path it is lower-risk, and 175 GiB is enough on its own to clear the alert.
- Target `data_lvmt_m2` is a **thin** pool: the 175 GiB raw volume becomes thin-provisioned there. After the move, `data_lvmt_m2` thin data usage rises by however much of the 175 GiB is actually written (worst case +175 GiB → pool still well under capacity: 473G+175G ≈ 648G of ~1.15T pool data ≈ 56%). **Verify** post-move that the thin pool data% stays comfortable.
- **Trade-off:** the cache disk moves from a dedicated SATA SSD to the `data_lvmt_m2` pool (NVMe `/dev/nvme1n1` + SATA `/dev/sdb` mixed). If `cache-sda` is a performance-sensitive cache, NVMe-backed `data_lvmt_m2` is arguably *faster*, so this is neutral-to-positive on performance. Confirm with the user what `cache-sda` backs (it is a guest-internal "cache" volume, likely a ZFS L2ARC/bcache/app cache inside nemesis).
- **Online vs downtime:** ONLINE. No guest reboot.

### Option B — Reclaim space without moving data (snapshots / orphans)

Investigation found **no snapshots** and **no orphaned volumes** on `data_lvm_2.5ssd1`. Therefore Option B yields **0 GiB** of relief on this storage. (The only reclaimable cruft is the two stale `unused0`/`unused2` *config* lines, which already point at non-existent `data_lvmt_m2` LVs and free nothing here.) **Not viable as a fix** — listed only to document that it was evaluated.

### Option C — Grow the physical disk / VG

Replace the 512 GB SSD with a larger one, or add a second PV to the VG. Requires hardware not currently free and (for a disk swap) VM downtime plus a `pvmove`/restore. **High effort, deferred.** Keep as the long-term answer if VM 100 genuinely needs >475 GiB of SSD-local thick storage; otherwise Option A makes it unnecessary.

---

## Recommendation

**Do Option A:** live-move `scsi3` (`vm-100-cache-sda`, 175 GiB) from `data_lvm_2.5ssd1` to `data_lvmt_m2` with `qm move-disk` while VM 100 stays running. It is online, reversible (move it back if needed), and on its own brings the storage from 99.59% to ~63%. If after confirming with the user the cache disk turns out to be safely disposable, an even cheaper variant is to detach+delete it — but **moving** is the safe default and is what this plan executes.

Keep Option C (bigger SSD) on the backlog as the structural fix only if nemesis's SSD-local footprint is expected to keep growing.

## Task 2: Live-move the cache disk (online, mutating)

**Files:** none (PVE host `sienar`). This is the one mutating step.

- [ ] **Step 1: Kick off the online move of `scsi3` to `data_lvmt_m2`.**

```bash
ssh -o IdentitiesOnly=yes lo204@192.168.1.5 \
  "sudo -n qm move-disk 100 scsi3 data_lvmt_m2"
```

- `qm move-disk <vmid> <disk> <target-storage>` on a running VM performs a live drive-mirror. By default, on success it **automatically removes the source volume** (`--delete` defaults to on for `move-disk` in PVE 8 when the move completes) — confirm by watching the task output; if your PVE build leaves the source as `unusedN`, do Step 3.
- This is a long-running task (175 GiB copy over the local bus). Watch progress; do **not** interrupt.
- **Online vs downtime:** ONLINE. VM 100 keeps running. Guest I/O to the cache disk continues against the mirror.
- **Safety / rollback:** During the mirror the source is untouched; if the task fails or is aborted, the disk remains on `data_lvm_2.5ssd1` (no change). If it succeeds you can reverse it later with `qm move-disk 100 scsi3 data_lvm_2.5ssd1` (space permitting).

- [ ] **Step 2: Verify the move landed and the alert pressure is relieved.**

```bash
ssh -o IdentitiesOnly=yes lo204@192.168.1.5 \
  "sudo -n qm config 100 | grep -E '^scsi3:'; echo ---; \
   sudo -n lvs data_lvm_2.5ssd1; echo ---; \
   sudo -n pvesm status -storage data_lvm_2.5ssd1; echo ---; \
   sudo -n pvesm status -storage data_lvmt_m2"
```

- **Expect:** `scsi3: data_lvmt_m2:vm-100-cache-sda,...`; `lvs data_lvm_2.5ssd1` now shows **only** `vm-100-disk-0` (300 GiB); `data_lvm_2.5ssd1` ~63% used; `data_lvmt_m2` data% risen but still well under capacity.
- **Safety:** Read-only verification.

- [ ] **Step 3 (only if the source was NOT auto-deleted): reclaim the leftover source LV.**

If `qm config 100` now shows the old volume as `unusedN: data_lvm_2.5ssd1:vm-100-cache-sda`, it is still occupying 175 GiB on `/dev/sda`. Remove it **only after** confirming Step 2 shows the disk is live on `data_lvmt_m2`:

```bash
# Identify the unused slot first:
ssh -o IdentitiesOnly=yes lo204@192.168.1.5 "sudo -n qm config 100 | grep -i unused"
# Then free it (replace unusedN with the actual slot):
ssh -o IdentitiesOnly=yes lo204@192.168.1.5 "sudo -n qm disk unlink 100 --idlist unusedN"
```

- **Safety:** Destroys the stale copy on `data_lvm_2.5ssd1` — irreversible. Triple-check Step 2 confirms the disk is healthy on `data_lvmt_m2` and the VM still boots/serves before unlinking. The live copy on `data_lvmt_m2` is the source of truth at this point.
